# M4: indexer

Threaded reads `at.threaded.*` records from the whole network, not only the
ones written through its own forms. A hydrant indexer runs beside Threaded,
finds every account that holds Threaded records, and streams their creates,
edits, and deletes in order. Every item goes through `accept`, the same path
as the web form. The design is in `0001-design.md`, sections 3.4 and 3.5.

## Done when

- A submission written straight to `steve.is.angstridden.net`'s repo, not
  through Threaded, appears on a local build within seconds, under
  `at.threaded.dev.*`.
- Editing and deleting that record in the repo edits and deletes the story.
- A story Threaded wrote comes back through the stream and is not indexed
  twice.
- A fresh database fills from hydrant's replay alone: stories, comments,
  public votes, handles.
- Deactivating an account hides its posts; reactivating shows them.
- `/admin` shows the stream's lag. A URL changed after the edit window shows
  in the Detached tab.
- `make check` and `make a11y` pass.

## hydrant

hydrant is built from a pinned commit of
`tangled.org/did:plc:dfl62fgb7wtjj3fcbb72naae/hydrant` (MIT licensed) and runs
as its own process. It serves its API on a Unix socket only, so the
management endpoints never reach the network.

| Setting | Production | Local |
|---|---|---|
| `HYDRANT_DATABASE_PATH` | `/var/lib/hydrant/db` | `./hydrant.db` |
| `HYDRANT_API_BIND` | `unix:/run/hydrant/api.sock` | `unix:./hydrant.sock` |
| `HYDRANT_API_SOCKET_MODE` | `0660`, group `threaded` | default |
| `HYDRANT_FILTER_SIGNALS` | `at.threaded.submission,at.threaded.comment` | the same under `at.threaded.dev.` |
| `HYDRANT_FILTER_COLLECTIONS` | the signals plus `at.threaded.vote` | the same under `at.threaded.dev.` |
| `HYDRANT_PLC_URL` | `https://plc.directory` | the same |
| `HYDRANT_DATA_COMPRESSION` | `lz4` | the same |
| `HYDRANT_CACHE_SIZE` | `32` | default |

Signals and collections are exact NSIDs, never `at.threaded.*`: a wildcard
also matches `at.threaded.dev.*`, and hydrant's crawler (lightrail) rejects
wildcard signals. hydrant's default PLC directory, `https://plc.wtf`, answers
with a redirect hydrant does not follow, which fails every backfill, so
`HYDRANT_PLC_URL` is set. Defaults stay for the rest: the firehose relay, the
lightrail crawler, full signature checks, and stored history.

At the pinned commit, `bbd9b93`, hydrant builds on macOS with `cargo build
--release`. Run with the local settings, it found the test account through
lightrail, backfilled it, and replayed its `at.threaded.dev.*` submission and
comments on `/stream?cursor=0`.

On the droplet (2 GB of RAM, Ubuntu), hydrant built and ran a trial with the
dev settings: both accounts backfilled, and it used 28 MB of memory with
`HYDRANT_CACHE_SIZE=32`. What the build needs there:

- `cmake`, and `.cargo/config.toml` moved aside, as hydrant's own Dockerfile
  does, so it links with the system linker instead of clang and `wild`.
- About 5 GB of swap: the final crate is compiled as one unit with LTO and is
  killed at 1 GB of swap. Build output takes about 1.7 GB until `cargo clean`.
- The lockfile updates below, applied with `cargo update -p NAME --precise
  VERSION` before building. A plain `cargo update` fails on hydrant's GitHub
  git dependencies.

hydrant's lockfile at the pinned commit has 17 known vulnerabilities. These
updates within the same major versions fix 13: `h2` 0.4.20, `rustls` 0.23.46,
`tokio` 1.54.1, `quinn-proto` 0.11.19, `crossbeam-epoch` 0.9.21, `scc` 3.8.8,
`anyhow` 1.0.104, `ctutils` 0.4.6, `zstd-sys` 2.1.2+zstd.1.5.7,
`async-compression` 0.4.51, and `compression-codecs` 0.4.46. Of the rest:

| Advisory | Status |
|---|---|
| `crypto-bigint` 0.5.5, RUSTSEC-2026-0387 | Not exploitable in hydrant: it only verifies signatures, with public keys, and holds no private key. Removed by patching jacquard 0.13 onto the 0.14 curve crates, as `third_party/` does for 0.12, before production |
| `zstd` 0.13 and `zstd-safe` 7, in hydrant's `fjall` and `lsm-tree` forks | Never run with `HYDRANT_DATA_COMPRESSION=lz4`, set on a new database; the journal already defaults to `lz4`. `POST /db/train` would run it and is never called. Fixed upstream only, in those forks |

## Reading the stream

`THREADED_HYDRANT_SOCKET` names hydrant's socket. Unset, the indexer is off
and Threaded works as in M3; local development without hydrant still works.

A task in the `threaded` process holds a websocket to `/stream` over the
socket, starting from the cursor in `stream_cursor`. Each event is applied,
then the cursor moves past it, in the same transaction where the event
changes rows. On disconnect it reconnects with backoff from the stored
cursor. Applying an event twice changes nothing, so a replay after a crash is
safe.

| Event | Applied as |
|---|---|
| submission create | `accept_story` with `Source::Network` |
| comment create | `accept_comment`; its subject and parent are found by AT-URI |
| vote create | an upvote, when the author has signed in here and may upvote |
| submission update | the author's edit; a moderator's override stays in force |
| comment update | the author's edit |
| any delete | the author's delete, as on the web |
| identity | the handle is checked at once, as sign-in and the daily re-check do, and stored with the same one-holder rule |
| account | `active: false` hides the account's posts until `active: true` |

Rules for network records:

- **Links.** Only `https` links are accepted, as on the web form; a submission
  with any other link is not indexed.
- **Time.** A live event's time is when it arrives; the record's `createdAt`
  is not trusted, so it cannot dodge rate limits or jump the front page. A
  backfilled event (`live: false`) keeps its `createdAt`, clamped to the
  arrival time.
- **Authors.** A DID that has never signed in gets a user row, as a New
  account. Its handle comes from `GET /repos/{did}` and shows only once
  verified.
- **Triage.** Live items are queued for triage when it is on. Backfilled
  items are not: they are old, and triaging them would start with a backlog
  bill.
- **Order.** hydrant keeps each repo in order, not the network. A comment
  whose story or parent is not indexed yet waits in `pending_records` and is
  applied when its subject arrives, or dropped after a day.
- **Threaded's own writes** come back as creates with a known AT-URI and
  change nothing. An update whose CID matches the stored one changes nothing.
- **Votes.** One vote per account and subject: a vote record for a subject the
  user already upvoted here attaches its AT-URI to that vote.
- **Link changes.** An update that changes a story's URL after the edit
  window detaches the story: it is hidden and logged, and appears in the
  Detached tab.

## Tracking accounts

hydrant discovers accounts that hold submissions or comments. Accounts that
only vote are added explicitly: Threaded sends each DID to `PUT /repos` when it
signs in, and at startup for every DID that has signed in, so their public
votes arrive.

## Identity on user review

`GET /repos/{did}` gives the handle and PDS host for the user review page.
The account's age comes from its PLC log's first operation, fetched on
demand with a short timeout and shown only for `did:plc`. Handle history comes
from identity events recorded from M4 on.

## Schema

Migration `0006_indexer.sql` adds `stream_cursor`, `pending_records`,

## Tasks

In order; each lands with its tests.

1. **hydrant locally.** Built from the pinned commit; a `make hydrant` target
   runs it with the local settings above.
2. **Client.** HTTP and websocket over a Unix socket: `/stream`,
   `/stream/head`, `GET` and `PUT /repos`.
3. **Applying events.** A pure step from one stream event to store changes,
   with the rules above, tested event by event without hydrant.
4. **The consumer.** The task, the cursor, reconnects, and `pending_records`.
5. **Accounts.** `PUT /repos` on sign-in and at startup; identity and account
   events; hiding inactive accounts.
6. **Moderation.** The Detached tab, stream lag on `/admin`, identity on user
   review.
7. **Docs and deploy.** hydrant's systemd unit and build on the droplet, the
   README, the design doc, the deck.
